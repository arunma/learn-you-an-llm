The Entrance, Exit, and Thinking Style of the model
?
The intuition

Computers can't do math on words. Raw token IDs like 50256 are just arbitrary integers — the number itself carries no meaning. Three architectural elements bridge the gap between text and computation.

wte — The Entrance
A giant lookup table. Token ID → 384 floats encoding meaning.

Shape: (50,257 × 384)
Params: 19.3M learnable

ID 2746 → row 2746 → [0.21, −0.54, 0.88, …]
Pure lookup — no matrix multiply.
lm_head — The Exit
Projects 384-dim context back to 50,257 scores.

Shape: (384 → 50,257)
Output: one logit per vocab token

Highest logit = predicted next token.
Shares weights with wte (weight tying).
n_head — Thinking Style
Divides 384 dims into 6 specialist perspectives.

Split: 384 ÷ 6 = 64 dims per head
Pattern: view() → transpose() → parallel attention

Each head learns its own focus. Results concatenated back to 384.
▦
Visual — n_head specialisation
The photo analogy — looking at "a cat sitting on a mat"

With 1 head: look at everything at once — trying to understand colour, shape, relationships, text all simultaneously. Limited capacity, no specialisation.

With 6 heads (each sees only 64 of 384 dims):

Head 0 → grammar relationships?
Head 1 → topic / subject matter?
Head 2 → nearby context?
Head 3 → coreference ("it" = what)?
Head 4 → long-range dependencies?
Head 5 → positional patterns?
The constraint that creates specialisation Each head only sees 64 of the 384 dimensions. It cannot try to track everything — it is forced to develop a focused perspective. Scarcity is what makes the heads diverge. The model learns what each head specialises in — you never assign roles manually.

Logits, Softmax, and Cross-Entropy Loss
The output pipeline — from context vectors to training signal
?
The problem

After the transformer blocks finish processing, each token position holds a 384-dim vector. But the model's job is to predict the next token from 50,257 possibilities. Three operations convert that vector into a training signal.

▦
Visual — the three-step pipeline
① Logits — raw scores
Output of lm_head. Not probabilities — just rankings. Can be any value, positive or negative.

"cat" → 8.7 "sat" → 6.2 "the" → 2.1 "jumped" → −1.4

Negative = unlikely, not impossible. Don't sum to anything meaningful yet.
② Softmax — probabilities
Three steps: exp() → sum → divide.
Result sums to exactly 1.0.

exp(8.7) = 6002.9
exp(6.2) =  492.7
sum      = 6505.4

"cat" → 6002.9/6505.4 = 92.3%
Ranking is preserved. Only scale changes.
③ Cross-entropy — loss
loss = −log(prob of correct token)

95% correct → −log(0.95) = 0.05 ✓
50% correct → −log(0.50) = 0.69
 1% correct → −log(0.01) = 4.61 ✗
 0% correct → −log(0.00) = ∞

One scalar. Flows backward through every layer during training.
{ }
Implementation
# ── TRAINING ─────────────────────────────────────────────────────────
logits = self.lm_head(x)             PT  # (B, T, 50257) raw scores

loss = F.cross_entropy(              PT  # fused log-softmax — numerically stable
    logits.view(-1, vocab_size),     NC  # (B*T, 50257) — flatten for PyTorch
    targets.view(-1)                 NC  # (B*T,)       — flatten targets
)
# Returns one scalar — average loss across all B*T token predictions
loss.backward()   PT  # nudge every weight to reduce this number

# ── INFERENCE ────────────────────────────────────────────────────────
last_logits = logits[:, -1, :]            NC  # (B, 50257) — last position only
probs = F.softmax(last_logits, dim=-1)    PT  # probabilities summing to 1

# Option A — greedy (deterministic, always picks highest)
next_token = probs.argmax(dim=-1)         PT

# Option B — sampling (creative, weighted random)
next_token = torch.multinomial(probs, 1)  PT

idx = torch.cat([idx, next_token], dim=1) PT  # append and loop
★
Key insights
Never softmax before F.cross_entropy F.cross_entropy applies log-softmax internally in a fused, numerically stable operation. Softmaxing first produces numbers like 0.9999997 — log() loses floating-point precision and errors accumulate across B×T predictions.
Training vs inference — the key difference Training: use ALL T positions simultaneously, compare against targets, compute loss.
Inference: use only the LAST position's logit (logits[:, -1, :]), no targets, softmax to pick next token.
The causal mask preview Attention scores are (T, T) pairwise relevance ratings. The causal mask sets scores above the diagonal to −∞ before softmax — token at position t cannot attend to positions t+1, t+2, …. After softmax, −∞ becomes zero probability. Future tokens contribute nothing.

Part 0: Foundations
Numbers, vectors, and matrices — the building blocks of everything

0.1 Why We Need Numbers

Neural networks only understand one language: numbers. Text is meaning, poetry, instruction—but a neural net sees zeros and ones, addition and multiplication. So our entire journey begins with a single, foundational problem:

The Core Problem How do we convert human language—words, sentences, paragraphs—into numbers that preserve meaning and let machines predict what comes next?

The answer involves three transformations, each building on the last:

Text → Token IDs → Embeddings → Tensors→ Model processes

Throughout this tutorial we'll work with a toy vocabulary to make the math concrete. Our examples use:

  • Batch size B = 12 (12 sequences processed together)
  • Context length T = 1024 (sequences up to 1024 tokens)
  • Embedding dimension C = 384 (384 features per token)
  • Vocabulary size V = 50,257 (GPT-2's vocabulary)

These are the same numbers used throughout. When you see a shape like (B, T, C), substitute: (12, 1024, 384).

?
Why it exists

Neural networks are just giant calculators. They add, multiply, and apply nonlinear squashing functions. They have no native understanding of strings, words, or letters. Feeding "hello" into a neural network makes no more sense than feeding a love poem to a calculator. So before the network can do anything, we must translate every word to a number.

0.2 Vectors and the Embedding Matrix

Let's zoom in on the embedding matrix. This single object is so fundamental that understanding it deeply will pay dividends later.

Column Vectors: How Embeddings Are Stored

An embedding is a column vector — a list of numbers stacked vertically. When we write the embedding for "cat" in 4 dimensions, we write:

cat_embedding =
[ 0.2 ] ← dimension 0
[ 0.8 ] ← dimension 1
[ 0.3 ] ← dimension 2
[ 0.5 ] ← dimension 3

Each number is a dimension or feature. We don't usually know what each dimension means — the network learns that during training. One dimension might capture "animacy" (cat is alive), another "softness," another "cuteness." Or none of those. The point is: we let the network figure out what's useful.

Why column vectors? Matrix multiplication is the dominant operation in neural networks. Shapes must align:

Weight matrix × Input vector = Output vector
(3 × 4) × (4 × 1) = (3 × 1) ✓

Column vectors make this work naturally. More on matrix multiplication in section 0.3.

The Embedding Matrix: Storing All Word Vectors

Instead of storing embeddings one at a time, we stack them all together into a single giant matrix. Each row holds one word's embedding: 

# Embedding Matrix: (V × C) = (50,257 × 384)
             Dim 0   Dim 1   Dim 2   ...  Dim 383
Token 0:     0.15    0.42    0.88   ...   0.21    ← row 0 = "the"
Token 1:     0.67    0.19    0.44   ...   0.53    ← row 1 = "a"
Token 2653:  0.65    0.48    0.72   ...   0.91    ← row 2653 = "cat"
...
Token 50256: 0.08    0.71    0.15   ...   0.62    ← row 50256 = "<|endoftext|>"

Lookup is trivial: 

token_id = 2653          # "cat"
embedding = emb_matrix[2653, :]
# → [0.65, 0.48, 0.72, ..., 0.91]
# shape: (384,) — a single embedding vector

When we process a batch of sequences, we perform batch indexing: given a (B, T) tensor of token IDs, we retrieve a (B, T, C) tensor of embeddings. This is the very first step inside the transformer.

Shape Notation Convention Throughout this tutorial, we use (B, T, C) shorthand for batch × time × channel. Substituting our concrete numbers: (12, 1024, 384). When you see a shape formula, always pair it with numbers.

0.3 A 5-Minute Matrix Multiplication Primer

Matrix multiplication is the heartbeat of neural networks. You'll see it hundreds of times. Let's understand it deeply via concrete examples.

The Rule: Inner Dimensions Must Match

For two matrices to multiply: 

A (m × n) × B (n × p) = C (m × p)
      ↑       ↑
   These must match!

The inner dimensions (n) must be identical. The result has dimensions from the outer edges: m and p.

How It Works: Row × Column Dot Products

Each element of the result is the dot product of a row from A and a column from B: 

A (2 × 3):          B (3 × 2):
[1  2  3]           [7   8]
[4  5  6]           [9  10]
                    [11 12]

Result[0,0] = Row 0 of A · Col 0 of B
            = [1, 2, 3] · [7, 9, 11]
            = (1×7) + (2×9) + (3×11)
            = 7 + 18 + 33 = 58

Result[0,1] = Row 0 of A · Col 1 of B
            = [1, 2, 3] · [8, 10, 12]
            = (1×8) + (2×10) + (3×12)
            = 8 + 20 + 36 = 64

Result[1,0] = Row 1 of A · Col 0 of B
            = [4, 5, 6] · [7, 9, 11]
            = (4×7) + (5×9) + (6×11)
            = 28 + 45 + 66 = 139

Result[1,1] = Row 1 of A · Col 1 of B
            = [4, 5, 6] · [8, 10, 12]
            = (4×8) + (5×10) + (6×12)
            = 32 + 50 + 72 = 154

Final result:
[58   64]
[139  154]

Matrix × Vector (Most Common in ML)

This is the case you'll see most often. A weight matrix multiplies an input vector to produce an output vector: 

W (3 × 4):           x (4 × 1):
[1  2  3  4]         [10]
[5  6  7  8]      ×  [20]
[9 10 11 12]         [30]
                     [40]

Output[0] = [1,2,3,4] · [10,20,30,40]
          = 1×10 + 2×20 + 3×30 + 4×40
          = 10 + 40 + 90 + 160 = 300

Output[1] = [5,6,7,8] · [10,20,30,40]
          = 5×10 + 6×20 + 7×30 + 8×40
          = 50 + 120 + 210 + 320 = 700

Output[2] = [9,10,11,12] · [10,20,30,40]
          = 9×10 + 10×20 + 11×30 + 12×40
          = 90 + 200 + 330 + 480 = 1100

Result:
[300]
[700]
[1100]

Interpretation: each row of W is a "detector" or "feature extractor."
Row 0 detects one pattern, row 1 detects another, row 2 detects a third.

The Dot Product: The Atomic Operation

The dot product of two vectors measures how much they "agree." It's the fundamental building block of everything: 

a = [2, 3, 4]
b = [5, 6, 7]

dot(a, b) = (2×5) + (3×6) + (4×7)
          = 10 + 18 + 28
          = 56

Intuition: If both vectors point in the same direction, the dot product is large and positive. If they point in opposite directions, it's large and negative. If they're perpendicular, it's zero.

Why This Matters Dot products measure similarity. In embeddings, a high dot product between two embedding vectors means those words are semantically close. In attention (coming later), dot products between query and key vectors determine which tokens attend to which.

0.4 Word2Vec — Learning Static Embeddings

We've now seen how embeddings are stored and manipulated mathematically. But where do these numbers come from? How does a network learn that "cat" and "dog" should have similar vectors?

Word2Vec (2013) was the first breakthrough: a simple, elegant training procedure that produced meaningful embeddings. Here's the insight:

The Distributional Hypothesis Words that appear in similar contexts have similar meanings. If "cat" and "dog" both appear near "pet," "furry," "meow"/"bark," then their embeddings should be close in space.

The Skip-Gram Architecture

Word2Vec uses a simple neural network with one hidden layer: 

Input (one-hot)           Hidden (embedding)       Output (logits)
5 dimensions       →      3 dimensions      →     5 dimensions
[0,0,1,0,0]                [0.8,0.3,0.4]          [0.43, 0.48, 0.74, 0.49, 0.77]
(select "sat")             (W1 projects)          (W2 projects)
                                                   ↓ softmax
                                                   [0.17, 0.18, 0.23, 0.18, 0.24]

Training data comes from the corpus as (center_word, context_word) pairs. The task: given "sat," predict surrounding words like "cat," "on," "mat."

The Two Matrices: W1 and W2

Word2Vec trains two weight matrices simultaneously:

Matrix Shape Role After Training
W1 (Input → Hidden) (V × C) = (5 × 3) "What is this word?" Used as embeddings
W2 (Hidden → Output) (C × V) = (3 × 5) "What words surround it?" Sometimes averaged with W1

Each row of W1 is a word's embedding. Each column of W2 is a word viewed as a "context word" — what does this word offer when it appears around others?

Worked Example: Forward Pass

Let's process the pair (center="cat", target="sat") step by step: 

Step 1: One-hot encode "cat"
input = [0, 1, 0, 0, 0]  ← only position 1 is "on"

Step 2: W1 matrix (5×3)
         Emb0  Emb1  Emb2
"the":  [0.2   0.5   0.1]
"cat":  [0.8   0.3   0.4]   ← we'll select this row
"sat":  [0.1   0.9   0.2]
"on":   [0.7   0.2   0.5]
"mat":  [0.4   0.6   0.8]

hidden = W1.T × input = [0.8, 0.3, 0.4]
         ↑
         The one-hot vector selects exactly row 1 (cat's embedding)!

Step 3: W2 matrix (3×5)
           "the"  "cat"  "sat"  "on"  "mat"
Emb0:     [0.3    0.1    0.6    0.2   0.4]
Emb1:     [0.5    0.8    0.2    0.7   0.3]
Emb2:     [0.1    0.4    0.5    0.3   0.9]

scores = W2.T × hidden
       = [0.3  0.5  0.1] × [0.8]
         [0.1  0.8  0.4]   [0.3]
         [0.6  0.2  0.5]   [0.4]
         [0.2  0.7  0.3]
         [0.4  0.3  0.9]

       = [(0.3×0.8 + 0.5×0.3 + 0.1×0.4),      ← score for "the"   = 0.43
          (0.1×0.8 + 0.8×0.3 + 0.4×0.4),      ← score for "cat"   = 0.48
          (0.6×0.8 + 0.2×0.3 + 0.5×0.4),      ← score for "sat"   = 0.74 ✓ HIGHEST
          (0.2×0.8 + 0.7×0.3 + 0.3×0.4),      ← score for "on"    = 0.49
          (0.4×0.8 + 0.3×0.3 + 0.9×0.4)]      ← score for "mat"   = 0.77

Step 4: Softmax
Sum = 0.43 + 0.48 + 0.74 + 0.49 + 0.77 = 2.91
probabilities = scores / sum
              = [0.15, 0.16, 0.25, 0.17, 0.26]

The model correctly gives highest probability to "sat"! ✓

Negative Sampling: Making Training Tractable

Computing softmax over 50,000 words is expensive. Word2Vec uses a clever trick: instead of predicting all words, just distinguish real neighbors from random noise.

Negative Sampling Intuition Real pairs (center, context) should score high. Random pairs (center, random_word) should score low. We only compute loss for a small set of negative samples, not all 50,000 non-neighbors. 
With negative sampling:

Positive pair ("cat", "sat"):
  score = dot(embedding_cat, embedding_sat) = 0.74
  prob = sigmoid(0.74) = 0.68
  target = 1 (this is a real context)
  loss = -log(0.68) = 0.39  ← push embeddings closer

Negative pair ("cat", "airplane"):
  score = dot(embedding_cat, embedding_airplane) = 0.22
  prob = sigmoid(0.22) = 0.55
  target = 0 (random word, not context)
  loss = -log(1 - 0.55) = -log(0.45) = 0.80  ← push apart

Total loss ≈ average of these ≈ 0.6 (computed for multiple negatives)
Gradients update W1 and W2 to minimize this loss.

What Word2Vec Actually Learns

After training on billions of (center, context) pairs from a large corpus: 

"cat"        → [0.65, 0.48, 0.72, ...]
"dog"        → [0.63, 0.50, 0.71, ...]   ← very similar! (both pets)
"kitten"     → [0.64, 0.47, 0.73, ...]   ← also similar

"bank" (ambiguous)    → [0.45, 0.38, 0.51, ...]   ← compromise

Famous arithmetic:
king - man + woman ≈ queen
[k.vectors] - [m.vectors] + [w.vectors] ≈ [q.vectors]

The geometry of embedding space captures semantic relationships. Words that co-occur move toward each other. This is the power of unsupervised learning on unlabeled text.

?
Why it exists

We need initial representations of words before we can build larger models. Word2Vec showed that a simple neural network trained to predict context can learn meaningful geometric embeddings from raw text, with no manual labeling.

0.5 Static vs Contextual Embeddings — The Motivation for Attention

Word2Vec is powerful, but it has a critical limitation that motivated decades of follow-up research.

The "Bank" Problem

Consider the word "bank." It has at least two distinct meanings:

  • "river bank" — the ground beside a stream
  • "deposit bank" — a financial institution

In a large corpus, "bank" appears in both contexts: 

"I walked along the river bank"
"I deposited money at the bank"
"The bank teller helped me"
"The river bank was muddy"

During Word2Vec training, the algorithm sees both contexts and updates "bank"'s embedding to be similar to both "river" and "deposit." The result: a single, static compromise vector. 

embedding_bank = [0.45, 0.38, 0.51, ...]  ← single, fixed vector

dot(bank, river)  = 0.72   ✓ high (shares river context)
dot(bank, deposit) = 0.68  ✓ high (shares finance context)

But which meaning is "bank" in THIS sentence?
Word2Vec has no way to know. The vector is the same regardless.
The Limitation Word2Vec treats each word as having exactly one embedding, regardless of context. This is why it's called static embeddings. The vector for "bank" is identical whether the sentence is about rivers or money.

What We Need: Context-Dependent Representations

Imagine if the network could compute different representations of "bank" depending on surrounding words: 

In "river bank":
  bank_representation = [0.91, 0.13, 0.82, ...]  ← closer to "river"

In "deposit bank":
  bank_representation = [0.15, 0.87, 0.31, ...]  ← closer to "deposit"

Same word, different vectors, determined by context!
This is a "contextual" embedding.

This is the motivation for RNNs, LSTMs, and ultimately Transformers. Each of these architectures solves a version of the same problem: how do we compute context-dependent representations?

We'll see this journey unfold in Part 0.5 and then throughout the tutorial.

Part 0.5: The Sequence-Modelling Lineage
From Word2Vec to Transformers: How each architecture solved what the previous one couldn't

We've established that Word2Vec learns static embeddings through clever matrix operations. But Word2Vec has no concept of sequence or order. "cat sat" and "sat cat" are identical to it—just two words appearing in context.

This section traces the intellectual lineage of sequence modelling: the chain of architectures that progressively unlocked longer memory, more parallelism, and richer contextual understanding. Understanding this arc is crucial before diving into nanochat's transformer implementation.

L.1 The Problem of Order — Word2Vec Is Bag-of-Words

Word2Vec operates on context windows, but it treats words as an unordered set. 

Sentence: "The cat sat on the mat"
Window around "sat" (size 2): ["cat", "on"]

Word2Vec never encodes that "cat" comes BEFORE and "on" comes AFTER.
It just knows: "cat" and "on" are both in sat's neighborhood.

"on sat cat" has the same window context.
Word2Vec treats both identically.
The Limitation Order matters in language. "Dog bites man" means something very different from "Man bites dog." Word2Vec cannot distinguish these.

To handle order, we need a model that processes words sequentially, remembering what came before and using that to inform predictions about what comes next.

Enter the RNN.

L.2 RNN — Embeddings Meet Sequence

The Recurrent Neural Network (RNN) adds one revolutionary idea: hidden state memory that is updated at every time step.

The Core Equation

h_t = tanh(W_x × x_t + W_h × h_{t-1} + b)

Where:
  h_t       = hidden state at time t (the "memory")
  x_t       = input at time t (word embedding from Word2Vec)
  h_{t-1}   = hidden state from previous time step (carries history)
  W_x       = weight matrix for input transformation
  W_h       = weight matrix for recurrent transformation
  b         = bias
  tanh      = squashing nonlinearity (outputs in [-1, 1])

The beauty: the same weights W_x and W_h are reused at every time step. This allows the network to handle sequences of any length and learn a general rule for "how to combine a new word with the history so far."

How the Same Weights Produce Different Meanings

Here's the genius: despite using identical weights, the RNN computes different representations for the same word in different contexts: 

Scenario A: "river bank"
h_river = tanh(W_x × embedding_river + W_h × h_0 + b)
        = [0.6, 0.3]

h_bank = tanh(W_x × embedding_bank + W_h × [0.6, 0.3] + b)
       = [0.82, 0.21]   ← influenced by river!

Scenario B: "deposit bank"
h_deposit = tanh(W_x × embedding_deposit + W_h × h_0 + b)
          = [0.2, 0.8]

h_bank = tanh(W_x × embedding_bank + W_h × [0.2, 0.8] + b)
       = [0.19, 0.91]   ← influenced by deposit!

Same embedding_bank, same W_x and W_h, BUT:
- When h_{t-1} = [0.6, 0.3], we get h_t = [0.82, 0.21]
- When h_{t-1} = [0.2, 0.8], we get h_t = [0.19, 0.91]

The hidden state from context changes the output!
This is contextual representation at work.

L.3 Vanishing Gradients — Why RNNs Forget

RNNs are powerful, but they have a fatal flaw: gradients vanish during backpropagation through time.

Backpropagation Through Time (BPTT)

During training, we compute loss for the entire sequence and backpropagate gradients backward in time: 

Forward:  h_0 → h_1 → h_2 → ... → h_T → loss
Backward: h_0 ← h_1 ← h_2 ← ... ← h_T ← loss

At each step backward, the gradient is multiplied by:
  ∂h_t/∂h_{t-1} = tanh'(z_t) × W_h

Where tanh'(z) = 1 - tanh²(z) is the derivative of tanh.

Let's trace what happens: 

tanh derivative values at typical inputs:
  z = 0.0:  tanh'(z) = 1.00  (max possible)
  z = 0.5:  tanh'(z) = 0.79
  z = 1.0:  tanh'(z) = 0.42
  z = 2.0:  tanh'(z) = 0.07  ← already small
  z = 3.0:  tanh'(z) = 0.01  ← very small

Typical W_h values: 0.3 to 0.7

Combined per-step factor: tanh' × W_h ≈ 0.4 to 0.5

Gradient Decay Over Time

When the same small factor (≈0.4) is multiplied repeatedly: 

Suppose we have a sequence of 50 tokens.
Gradient at position T (output):    1.000
Gradient at position T-5:           (0.4)^5  ≈ 0.010
Gradient at position T-10:          (0.4)^10 ≈ 0.0001
Gradient at position T-20:          (0.4)^20 ≈ 0.0000001
Gradient at position 1:             (0.4)^50 ≈ 1e-20 ≈ 0

Concrete example: 0.1^10 = 0.0000000001 = 1e-10

The gradient at early positions is essentially zero. The network cannot learn from errors that depend on words at the beginning of the sequence.

The Problem An RNN processing 50 words cannot meaningfully update its weights based on the first word's contribution. Early context is effectively ignored. Long-range dependencies (e.g., pronoun references spanning 30 words) cannot be learned.

Why This Happens

RNNs have only one pathway for information and gradients: 

h_1 → h_2 → h_3 → ... → h_50

At every step: h_new = tanh(W_x × x + W_h × h_old + b)

Both the forward and backward passes go through the same repeated
multiplication of W_h (forward) and its derivative (backward).

With the same small factor applied 50 times, the signal dies.

The fix requires a different architecture that provides an alternative, protected pathway for information to flow unchanged over many steps.

L.4 LSTM — The Cell State Highway

The Long Short-Term Memory (LSTM) cell adds a brilliant solution: a second state variable, the cell state, that follows an additive update rule rather than a multiplicative one.

LSTM Architecture

LSTM has TWO state variables at each time step:
  - c_t: cell state (long-term memory, protected lane)
  - h_t: hidden state (working memory, output)

The cell state is updated additively:
  c_t = f_t ⊙ c_{t-1} + i_t ⊙ c_tilde
        ↑ forget old      ↑ add new

Where f_t and i_t are gated values (between 0 and 1).

The Gates: Learned Control**

LSTM introduces three learned gates that control information flow:

Gate Equation Purpose
Forget f_t = σ(W_f·[h_{t-1}, x_t] + b_f) How much old cell state to keep? (0=forget all, 1=keep all)
Input i_t = σ(W_i·[h_{t-1}, x_t] + b_i) How much new info to add? (0=ignore, 1=accept fully)
Output o_t = σ(W_o·[h_{t-1}, x_t] + b_o) What to expose as hidden state? (0=hide, 1=expose)
Candidate c_tilde_t = tanh(W_c·[h_{t-1}, x_t] + b_c) What new values to potentially add to cell state?

σ is sigmoid, which outputs a value between 0 and 1—perfect for gates. ⊙ is element-wise multiplication.

The Key Equation: Why Gradients Don't Vanish**

The cell state update is: 

c_t = f_t ⊙ c_{t-1} + i_t ⊙ c_tilde_t

Gradient flows backward as:
  ∂c_t / ∂c_{t-1} = f_t

This is the genius: the gradient is multiplied by f_t, which is
LEARNED and can be close to 1.0!

Contrast with RNN:
  ∂h_t / ∂h_{t-1} = tanh'(z_t) × W_h ≈ 0.4 to 0.5 (fixed, small)

With LSTM, the network learns WHEN to keep the gradient:
  If f_t ≈ 1.0:  gradient ≈ 1.0 × 1.0 × ... × 1.0 = 1.0  ✓ NO VANISHING
  If f_t ≈ 0.0:  gradient ≈ 0.0 (intentional forgetting)

The model has explicit control over gradient flow!

Over 50 timesteps with typical LSTM: 

RNN gradient at position 1:    ≈ (0.4)^50 ≈ 1e-20 ← nearly dead
LSTM gradient at position 1:   ≈ (0.85)^50 ≈ 0.000001 ← still alive!

(Assuming forget gates learn to stay at 0.85 on average)
The Breakthrough LSTMs solved the vanishing gradient problem by introducing a protected additive path. Information can flow across long sequences because the gradient can stay large on the cell state's highway. This enabled training on sequences of hundreds or thousands of tokens.

L.5 Encoder-Decoder for Machine Translation

Once LSTMs solved vanishing gradients, a new architecture pattern emerged for tasks like machine translation: the encoder-decoder architecture.

The Setup

Task: Translate English to French

Input:  "The cat sat" (English)
Output: "Le chat assis" (French)

Encoder:
  Processes English sequentially, compressing the entire meaning
  into a single "thought vector"

Decoder:
  Uses the thought vector to generate French word-by-word

Encoder Phase

Initial state: h_0_enc = [0, 0]

Process "The":
  h_1_enc = LSTM_enc(embedding_the, h_0_enc) = [0.2, 0.3]

Process "cat":
  h_2_enc = LSTM_enc(embedding_cat, h_1_enc) = [0.4, 0.5]

Process "sat":
  h_3_enc = LSTM_enc(embedding_sat, h_2_enc) = [0.7, 0.6]

Final hidden state (the "thought vector"):
  thought = h_3_enc = [0.7, 0.6]

This vector contains compressed information about the entire
English sentence. It becomes the seed for the decoder.

Decoder Phase

Initialize decoder with encoder's final state:
  h_0_dec = thought = [0.7, 0.6]

Start with special <START> token:
  h_1_dec = LSTM_dec(embedding_START, h_0_dec)
  logits_1 = W_out @ h_1_dec
  probs_1 = softmax(logits_1)
  token_1 = argmax(probs_1)  → "Le" (Le chat... French for "the cat")

Feed output back in:
  h_2_dec = LSTM_dec(embedding_Le, h_1_dec)
  logits_2 = W_out @ h_2_dec
  token_2 = argmax(softmax(logits_2))  → "chat"

Again:
  h_3_dec = LSTM_dec(embedding_chat, h_2_dec)
  token_3 = argmax(softmax(...))  → "assis"

Stop when we generate <END> token.

Output: "Le chat assis" ✓

The Bottleneck Problem

Here's the critical issue:

The encoder must compress an arbitrarily long sentence into a single vector. If the encoder processes a 50-word paragraph, all of that information flows through a single bottleneck: the final hidden state. thought_vector = [0.7, 0.6] (just 2 numbers! or 256 or 1024...) The decoder must reconstruct the entire meaning of a 50-word paragraph from this tiny vector. Information is lost.
The Limitation Encoder-decoder works well for short sequences but struggles with longer ones. A 256-dimensional thought vector cannot possibly capture all the nuance of a 1000-word article.

This bottleneck motivated the next breakthrough: instead of squeezing everything through one vector, let the decoder directly look back at all the encoder's hidden states.

L.6 The Bottleneck → Attention: The Leap

The solution to the bottleneck is elegant and revolutionary: attention.

Instead of: 

encoder h_1, h_2, h_3, ... h_T  →  [compressed thought] → decoder

We do: 

encoder h_1, h_2, h_3, ... h_T  → decoder can LOOK BACK at any h_i

The Core Idea

When the decoder is generating word t, it should be able to ask: "Which encoder hidden states are relevant to me right now?" Then it dynamically computes a weighted sum of all encoder states, weighted by relevance. 

At decoder timestep 2 (generating "chat" from encoder "cat"):

Decoder hidden state: h_2_dec = [0.45, 0.78]

Attention query question:
  "Which encoder states are relevant to my current goal?"

Compute relevance scores (using dot products):
  score_1 = dot(h_2_dec, h_1_enc)  =  0.34  ← "The"
  score_2 = dot(h_2_dec, h_2_enc)  =  0.71  ← "cat"  ✓ HIGH!
  score_3 = dot(h_2_dec, h_3_enc)  =  0.28  ← "sat"

Apply softmax to get weights:
  weight_1 = 0.18
  weight_2 = 0.61   ← mostly attending to "cat"
  weight_3 = 0.21

Compute weighted sum of encoder states:
  context = 0.18 × h_1_enc + 0.61 × h_2_enc + 0.21 × h_3_enc

Concatenate with decoder state:
  enhanced = [h_2_dec, context]

This enhanced representation is rich with information about:
  - What the decoder was thinking (h_2_dec)
  - What parts of the input are relevant (context)

Both pieces combined drive the prediction of "chat"

This is the birth of attention. No information is lost to a bottleneck. The decoder can directly inspect every encoder state and pick what it needs.

Why Attention Mattered Attention replaced the bottleneck problem with a content-based lookup mechanism. The decoder isn't limited by trying to cram meaning into one vector. It can distribute its focus across all encoder states, dynamically, based on relevance. This unlocked translation quality for longer sequences.

L.8 The Unifying Thread**

Every architecture in this lineage answers the same fundamental question, with increasing power:

Given a sequence of words, what is the richest possible representation of meaning that lets us predict what comes next?
  • Word2Vec: Meaning lives in geometric space. Similar words cluster together.
  • RNN: Meaning accumulates through time. A hidden state that evolves with each word.
  • LSTM: Important meaning needs a protected highway. A cell state that gates information.
  • Transformer: Meaning comes from direct comparison of all tokens. Every token attends to every other token, computing relevance on the fly.

None of these architectures discarded the previous one's insights. They generalized them:

  • RNN inherits Word2Vec embeddings
  • LSTM inherits RNN's sequence processing and adds a bypass (cell state)
  • Attention inherits the LSTM's bypass idea and applies it globally
  • Transformer inherits all the projection ideas and applies them three ways (Q, K, V)

This is the true lineage: each step solved what the previous step couldn't, while keeping the good parts.

# [NC] All code below — plain Python, no PyTorch needed
from collections import Counter

def get_pairs(vocab):
    """Count all adjacent pairs across the whole corpus."""
    pairs = Counter()
    for word, freq in vocab.items():
        symbols = word.split()
        for i in range(len(symbols) - 1):
            pairs[(symbols[i], symbols[i+1])] += freq
    return pairs

def merge_vocab(pair, vocab):
    """Replace winning pair everywhere in corpus."""
    new_vocab = {}
    bigram = ' '.join(pair)
    replacement = ''.join(pair)
    for word in vocab:
        new_vocab[word.replace(bigram, replacement)] = vocab[word]
    return new_vocab

vocab = {'l o w Ġ': 5, 'l o w e r Ġ': 2, 'n e w e s t Ġ': 6}
merge_rules = []          # this ordered list IS the tokeniser

for i in range(10):
    best  = max(get_pairs(vocab), key=get_pairs(vocab).get)
    vocab = merge_vocab(best, vocab)
    merge_rules.append(best)
    # merge_rules = [('l','o'), ('lo','w'), ('low','e'), ...]

# Encode new text: apply merge rules in order
def tokenise(text, merge_rules):
    words = [' '.join(list(w)) + ' Ġ' for w in text.split()]
    for (a, b) in merge_rules:
        words = [t.replace(f'{a} {b}', f'{a}{b}') for t in words]
    return [tok for t in words for tok in t.split()]

Phase 1 — Key takeaways

Six things that stick after Phase 1
  1. The tokeniser is pure Python. No PyTorch, no GPU, no training. It runs once on raw text and produces integer arrays on disk.
  2. Two designs, same interface. Char tokeniser uses stoi/itos dicts; tiktoken uses compiled Rust. Both expose encode(str) → list[int] and decode(list[int]) → str.
  3. BPE merge rules are the tokeniser — not the final vocabulary list. To encode new text, apply each merge rule in order to the character sequence.
  4. vocab_size flows into exactly two model layers — nn.Embedding at the input and nn.Linear (lm_head) at the output. Change tokeniser → change both.

Embeddings
How integer token IDs become float vectors, and how the model knows word order

After Phase 1, get_batch() returns idx of shape (B, T) = (12, 1024) — a grid of integers. Integers are arbitrary IDs. The number 2746 has no mathematical relationship to 2747. You can't do meaningful matrix multiplication on raw integers. Embeddings fix this — converting each integer into a 384-dimensional float vector where proximity encodes meaning.

The benefit is consistency.

Every vector entering the next sublayer has mean=0 and std=1. Attention weights don't have to cope with values that are sometimes 0.001 and sometimes 1000.

Training is dramatically more stable. Applied before attention and before FFN in every block (pre-norm pattern).
▦
Visual — SGD → Adam → AdamW
Plain SGD
weight = weight − lr × gradient

One fixed learning rate for all weights. Zigzags in ravines. Can't handle tiny and huge gradients simultaneously.
Adam (2015)
Tracks m (momentum) and v (variance) per weight.

update = lr × m / (√v + ε)

Every weight gets its own adaptive learning rate. Bug: weight decay gets rescaled by √v — loses effect.
AdamW (2017) ← nanochat
Adam + decay applied after gradient update — decoupled.

weight -= lr × m / (√v + ε) gradient
weight -= lr × λ × weight    decay, clean

Every weight decays by consistent λ × weight regardless of gradient size.

Adam internals — the "m" and "v" trackers

m (momentum / exp_avg): Running average of recent gradient directions. β₁=0.9 means "90% old direction + 10% new gradient." Acts like a heavy ball — smooths noise, doesn't stop instantly at small bumps.

v (variance / exp_avg_sq): Running average of recent gradient magnitudes squared. β₂=0.95 means "95% old size + 5% new gradient²." Tracks volatility.

The automatic gearbox: Dividing by √v gives each weight its own effective step size. Neglected weight (tiny v) → large step (gets a push). Exploding weight (huge v) → tiny step (moves cautiously). You never manually tune per-layer learning rates.

Phase 2 — Key takeaways

What Phase 2 actually taught
  1. Embedding = learnable lookup — nn.Embedding is a matrix; integer i selects row i. No matrix multiply happens at lookup time.
  2. Two embeddings, added element-wise. Token (wte) says what the token is; position (wpe) says where it sits. x = wte(idx) + wpe(pos) gives each token a unique "word + position" signature.
  3. LayerNorm normalises per vector, not per batch. Mean 0, std 1 along the feature dim. Re-scales with learnable γ, β. It stabilises training; it does not clip to ±1.
  4. The transformer block is one residual pass twice. x = x + Attention(LN(x)), then x = x + MLP(LN(x)). Skip connections keep gradients alive across depth.
  5. AdamW is Adam + decoupled weight decay. Per-parameter adaptive learning rates, momentum over past gradients, L2 penalty applied separately. Standard for LLM training.
  6. Gradient clipping is the seat belt. clip_grad_norm_ keeps one bad batch from blowing up weeks of training.
Phase 3
Causal Self-Attention
The heart of the transformer — how tokens attend to each other

This is the most important phase in the build. Everything before it was setup. The transformer's power comes entirely from what happens here: every token looks at every other token, scores how relevant each one is, and uses those scores to pull in information from across the sequence.

3.1 — Q, K, V Projections

?
Why three matrices? Why not compare embeddings directly?

The token embedding already carries 384 numbers describing the token. Why not just compare those directly? Because the embedding carries everything about a token at once. You need three specialised, separate views of it — each answering a different question, via three separate learned weight matrices.

▦
Visual — Q, K, V roles
Q — Query
"What am I looking for?"

The question a token is asking. Scored against every other token's Key to produce attention scores. Determines how much each other token is attended to.
K — Key
"What do I advertise I contain?"

The catalogue label. Matched against Queries. K determines whether a token gets attended to. Can be highly findable (strong K) while sharing something different in V.
V — Value
"What do I actually give away?"

Content retrieved when attention is high. V determines what flows when a token is attended to. Completely separate from K — this is why the model can learn nuanced retrieval patterns.
The library analogy You are the Query (searching "books about cats"). Each book's catalogue entry is a Key. The score = how well your query matches each key. The actual pages you read = the Value. A beautifully written book (high V) with a terrible catalogue entry (low K) will never be found. Q, K, V are separate for exactly this reason.

Phase 3.1 — Key takeaways

The Q/K/V projection step in six bullets
  1. Q, K, V come from the same x. Three learned linear projections of the same input produce three interpretations: Q (asking), K (advertising), V (offering).
  2. One fused nn.Linear(C, 3C) is the trick. Project to 3C in one matmul, then .split(C, dim=-1) into q, k, v — fewer kernel launches than three separate Linears.
  3. Heads are a .view(), not extra parameters. (B, T, C) becomes (B, T, n_head, head_dim) by reshaping memory. C = n_head × head_dim by construction.
  4. .transpose(1, 2) moves heads to the batch dimension. (B, T, n_head, head_dim) → (B, n_head, T, head_dim). Now every head×batch pair runs as an independent matmul on the GPU.
  5. Attention is Q @ Kᵀ / √d. The transpose puts K into the shape that lets every query compare against every key at once. √d keeps scores in a range softmax can handle.
  6. The (T, T) score matrix is the bottleneck. Memory grows with T². Doubling the context window quadruples attention memory — the reason long-context LLMs are expensive.
3.2
Attention Scores and Causal Masking
Q @ KT — The relevance matrix, and why future tokens must be blocked
?
Why it exists

After projecting each token into Query, Key, and Value spaces, the model must decide: for each token, which other tokens are most relevant? Self-attention answers this by computing a relevance score between every pair of tokens using the dot product Q @ KT. A high score means "these two tokens belong together in understanding the context." Then we apply a causal mask to prevent the model from cheating — attending to tokens it hasn't seen yet during generation.

def attention_forward(Q, K, V, causal_mask):
    # (B, n_h, T, d_h) for each of Q, K, V

    # Step 1: raw scores
    scores = Q @ K.transpose(-2, -1)  # shape: (B, n_h, T, T)

    # Step 2: scale by sqrt(d_h) to stabilize variance
    scores = scores / math.sqrt(d_h)  # (12, 6, 1024, 1024) ÷ 8

    # Step 3: apply causal mask
    # Lower triangle = future tokens
    scores = scores.masked_fill(causal_mask == 0, float('-inf'))

    # Step 4: softmax (stable because of scaling + masking)
    weights = torch.softmax(scores, dim=-1)  # normalize per row

    # Step 5: apply to values (next phase)
    output = weights @ V  # (B, n_h, T, d_h)

    return output
★
Key insights
Scaling prevents softmax collapse. Without dividing by √d_h, dot products in high dimensions (384) become huge — softmax becomes nearly one-hot (all weight on one token). Scaling by √64=8 keeps scores reasonable, producing smoother attention distributions that learn better.
Causal masking is essential for autoregressive models. During training, if token 10 could attend to token 15, the model would "know" the future. At inference time, token 15 doesn't exist yet, so the model would fail. Masking during training mirrors the inference constraint: never peek ahead.
The YouTube search analogy returns here. Q @ K is like searching a database: "How well does this token's query match other tokens' advertisements?" High dot product = good match = high attention weight. The causal mask simply removes future results from the search.
3.3
Softmax and Value Aggregation
Where context actually flows — weighted sum of values
?
Why it exists

Attention scores tell us how much to listen to each token. Now we aggregate the actual information. Softmax converts scores into a probability distribution (all non-negative, sum to 1), then we compute a weighted average of the Value vectors. This is where semantic content flows between tokens. Token A doesn't send a message to Token B — instead, B computes a weighted mixture of all tokens' values, weighted by how relevant B decided each was.

def softmax_and_aggregate(scores, V, causal_mask):
    # scores shape: (B, n_h, T, T)
    # V shape:      (B, n_h, T, d_h)

    # Step 1: mask before softmax
    scores = scores.masked_fill(causal_mask == 0, float('-inf'))

    # Step 2: softmax per row (last dimension)
    weights = torch.softmax(scores, dim=-1)  # each row sums to 1
    # Now shape: (B, n_h, T, T)
    # weights[b, h, i, j] = attention of token i to token j

    # Step 3: weighted sum of values
    # matrix multiply: (B, n_h, T, T) @ (B, n_h, T, d_h)
    output = weights @ V
    # Output shape: (B, n_h, T, d_h)
    # Each output token is a mixture of input values!

    return output, weights

Matrix multiply intuition: weights @ V is a dot product of each row of weights with each column of V. Since each row of weights sums to 1, the output is a weighted average of the rows of V — exactly what we want.

★
Key insight
This is where context flows. The attention mechanism is not about "sending a message." It is about each token pulling a mixture of other tokens' representations. The weights are learned: Q and K are optimized so that relevant tokens get high weights, irrelevant ones low weights. V carries the content. Over layers, tokens progressively blend contextual information, building richer representations.
Why separate softmax and aggregate? Pedagogically, they are two operations: softmax normalizes the scores, aggregation applies them. Computationally, they can be fused (PyTorch calls this F.scaled_dot_product_attention) for speed and numerical stability. For clarity in nanochat, they are separate.
3.4
Multi-Head Concat and Output Projection
Merging specialist perspectives back into a shared space
?
Why it exists

After computing attention independently in each of 6 heads (each working on 64 of the 384 dimensions), we must merge the results back. Head 0 may have learned "grammar patterns," Head 1 "semantic similarity," Head 2 "proximity." If we just concatenate them, we get 6×64=384 dims back, but the model has no way to decide which head insights matter. The output projection W_O is a learned matrix that combines head outputs, deciding how much to weight each head's perspective for the current task.

◆

The transpose-contiguous-view pattern: After attention, each head's output is scattered across the batch and head dimensions. transpose(-2, -1) moves the head dimension next to the embedding dimension, .contiguous() makes memory layout sequential (PyTorch requirement for reshape), then .view(B, T, C) merges the heads.

        x = x + self.attn(self.ln1(x))  # residual connection (Phase 4.1)

class CausalSelfAttention(nn.Module):
    def __init__(self, config):
        super().__init__()
        self.c_attn = nn.Linear(config.n_embd, 3 * config.n_embd)  # Q, K, V projections
        self.c_proj = nn.Linear(config.n_embd, config.n_embd)  # W_O: output projection
        self.n_head = config.n_head
        self.n_embd = config.n_embd
        self.register_buffer("bias", torch.tril(torch.ones(config.block_size, config.block_size)))

    def forward(self, x):
        # (B, T, C) → project to Q, K, V
        B, T, C = x.shape
        qkv = self.c_attn(x)  # (B, T, 3C)
        q, k, v = qkv.split(self.n_embd, dim=-1)

        # Reshape for multi-head: (B, T, C) → (B, T, n_h, d_h) → (B, n_h, T, d_h)
        q = q.view(B, T, self.n_head, C // self.n_head).transpose(1, 2)
        k = k.view(B, T, self.n_head, C // self.n_head).transpose(1, 2)
        v = v.view(B, T, self.n_head, C // self.n_head).transpose(1, 2)

        # Attention: (B, n_h, T, T)
        scores = (q @ k.transpose(-2, -1)) * (1.0 / math.sqrt(C // self.n_head))
        scores = scores.masked_fill(self.bias[:T, :T] == 0, float('-inf'))
        attn = torch.softmax(scores, dim=-1)

        # Aggregate: (B, n_h, T, d_h)
        out = attn @ v

        # ═══ PHASE 3.4: MERGE HEADS ═══
        # (B, n_h, T, d_h) → (B, T, n_h, d_h)
        out = out.transpose(1, 2)
        # Reshape back to (B, T, C)
        out = out.contiguous().view(B, T, C)
        # Project output: apply W_O
        out = self.c_proj(out)

        return out
★
Key insights
W_O is not optional — it is how the model learns which heads to trust. Imagine Head 3 learns "coreference resolution" (tracking pronouns) and Head 5 learns "random noise." W_O's gradients during training will learn to give Head 3 high weight and Head 5 low weight. Without W_O, the heads would be concatenated with fixed mixing — no specialization.
The transpose-contiguous-view sequence is a PyTorch idiom. After transpose(1, 2), the tensor is no longer stored contiguously in memory — it is a view with a reordered stride. .contiguous() reallocates memory to be linear, which .view() requires. This is purely a memory layout issue, not a semantic one.
Why "contiguous" is necessary: .view() reshapes a tensor assuming its elements are stored linearly. After .transpose(), strides are non-linear (memory jumps), so view would give the wrong result. .contiguous() reallocates to linear order. Modern PyTorch has .reshape() which handles both cases automatically.

Phase 4.1: Residual Connections

?
Why it exists

Deep networks face a fundamental problem: gradients shrink as they backpropagate through layers. In a 12-layer transformer without residuals, gradients can vanish before reaching early layers, making them impossible to train. Residual connections solve this by adding a direct shortcut: output = x + f(x) instead of output = f(x). This preserves the original signal while applying small contextual refinements.

◆
Visual — the gradient highway

After Layer 11:   0.8 × 0.1 = 0.08
...
After Layer 1:    8.0 × (0.1)^12 ≈ 0.00000008   ← nearly zero!

Layer 1 barely learns anything!
WITH RESIDUALS — Gradient stays strong everywhere
output = x + f(x)
doutput/dx = 1 + df(x)/dx
                ↑
           This "1" is the key!

Loss gradient:      8.0
After Layer 12:     8.0 × (1 + 0.1) = 8.8
After Layer 11:     8.8 × (1 + 0.1) = 9.68
...
After Layer 1:      stays large throughout!

The sculptor analogy
Building a sculpture. Imagine starting with a rough block of stone (initial embedding). Without residuals, Layer 1 discards the block and starts carving a new shape. If that shape is wrong, all downstream layers inherit the mistake. With residuals, Layer 1 makes small refinements to the block. Layer 2 refines further. By Layer 12, the original block (with identity information) is still present, but heavily sculpted by 12 refinements. Each layer is a small chisel mark, not a restart.

Phase 4.2: Layer Normalization

?
Why it exists

After a residual addition (x + f(x)), values can have wildly different scales across dimensions. Some dimensions might be 5.0, others -0.1. When these are fed into the next layer's Q, K, V projections, the matrix multiplies become numerically unstable and training diverges. Layer normalization rescales each token's vector to have mean 0 and standard deviation 1, stabilizing the signal for the next layer.

◆
Visual — step-by-step normalization
WORKED EXAMPLE — normalize a 4-dim token vector
Input: x = [3.02, -1.49, 3.77, 0.37]  ← wildly different magnitudes

Step 1: Compute mean
  μ = (3.02 + (-1.49) + 3.77 + 0.37) / 4 = 6.67 / 4 = 1.668

Step 2: Compute standard deviation
  Deviations from mean: [3.02-1.668, -1.49-1.668, 3.77-1.668, 0.37-1.668]
                      = [1.352, -3.158, 2.102, -1.298]

  Squared deviations: [1.828, 9.973, 4.418, 1.685]
  Variance = (1.828 + 9.973 + 4.418 + 1.685) / 4 = 4.476
  Std dev σ = √4.476 = 2.116

Step 3: Normalize to mean=0, std=1
  normalized[i] = (x[i] - μ) / σ

  normalized[0] = (3.02 - 1.668) / 2.116 = 0.639
  normalized[1] = (-1.49 - 1.668) / 2.116 = -1.492
  normalized[2] = (3.77 - 1.668) / 2.116 = 0.993
  normalized[3] = (0.37 - 1.668) / 2.116 = -0.613

  normalized = [0.639, -1.492, 0.993, -0.613]  ← mean ≈ 0, std ≈ 1

Step 4: Learned scale (γ) and shift (β)
  γ = [1.2, 0.8, 1.5, 0.9]    ← learned per dimension
  β = [0.1, -0.2, 0.0, 0.3]   ← learned per dimension

  output[i] = γ[i] * normalized[i] + β[i]

  output[0] = 1.2 * 0.639 + 0.1 = 0.867
  output[1] = 0.8 * (-1.492) - 0.2 = -1.394
  output[2] = 1.5 * 0.993 + 0.0 = 1.490
  output[3] = 0.9 * (-0.613) + 0.3 = -0.252

  output = [0.867, -1.394, 1.490, -0.252]

class LayerNorm(nn.Module):
    # PyTorch's nn.LayerNorm handles all steps above

    def __init__(self, n_embd, eps=1e-5):
        super().__init__()
        self.weight = nn.Parameter(torch.ones(n_embd))   # γ (scale)
        self.bias = nn.Parameter(torch.zeros(n_embd))    # β (shift)
        self.eps = eps  # small constant to avoid division by zero

    def forward(self, x):
        # x shape: (B, T, C)
        # normalize per token (across C dimension)
        mean = x.mean(dim=-1, keepdim=True)
        std = x.std(dim=-1, keepdim=True)
        normalized = (x - mean) / (std + self.eps)
        # apply learned scale and shift
        output = self.weight * normalized + self.bias
        return output


# In Block, LayerNorm is applied BEFORE attention (pre-norm architecture)
# This is more stable than post-norm (applying after residual)
x = x + self.attn(self.ln1(x))  # ln1 normalizes before feeding to attention
x = x + self.mlp(self.ln2(x))   # ln2 normalizes before feeding to FFN
★
Key insights
LayerNorm vs BatchNorm: BatchNorm (used in CNNs) normalizes across the batch dimension — "compare this pixel's value across all images in the batch." LayerNorm normalizes across the embedding dimension — "compare this token's dimensions to its own average." LayerNorm works identically regardless of batch size or sequence length, making it ideal for text.
Why γ and β are necessary: Pure normalization forces all tokens to have mean 0, std 1. But the model might genuinely need mean=2, std=3 in some dimensions to represent certain concepts. γ and β are learned parameters that let the model "undo" normalization where beneficial, while still getting stability during training.
Pre-norm vs post-norm: Nanochat uses pre-norm (apply LayerNorm before attention/FFN) because it is more stable for deep networks. The original Transformer used post-norm (apply after residual), but pre-norm trains faster and requires less learning rate tuning.

Phase 4.3: Feed-Forward Network

?
Why it exists

Self-attention gathers context — mixing signals from many tokens. The feed-forward network processes that context independently per token. Each token runs through a small neural network: expand from 384 → 1536 dims, apply ReLU to select active features, compress back to 384. This is where much of the model's factual knowledge is stored. Research shows removing FFN layers hurts factual recall more than removing attention.

  output = [0.71, 0.29, 0.63, 0.48]

class MLP(nn.Module):
    def __init__(self, config):
        super().__init__()
        self.c_fc = nn.Linear(config.n_embd, 4 * config.n_embd)
        self.gelu = nn.GELU()  # smoother than ReLU
        self.c_proj = nn.Linear(4 * config.n_embd, config.n_embd)

    def forward(self, x):
        # x shape: (B, T, C) = (12, 1024, 384)
        x = self.c_fc(x)      # (B, T, 384) → (B, T, 1536)
        x = self.gelu(x)      # activate
        x = self.c_proj(x)    # (B, T, 1536) → (B, T, 384)
        return x


# GELU vs ReLU:
# ReLU(x) = max(0, x)           hard cutoff at 0
# GELU(x) = x * Φ(x)            smooth probabilistic cutoff
#         = 0.5 * x * (1 + tanh(√(2/π) * (x + 0.044715*x³)))
#
# GELU is "softer" — useful features with value 0.1 aren't instantly zeroed.
# GPT uses GELU, not ReLU.
★
Key insights
The expansion is where the model reasons. The 1536-dim space is a "reasoning workspace" where the model detects many features simultaneously. Dimensions might encode "is this a number?", "does this word appear in dialogue?", "is this a programming language?", etc. ReLU gates these features, and W2 combines the active ones. This is far more expressive than a single matrix.
Why 4× expansion? The ratio d_ff / d_model = 4 is a design choice. Original Transformer used 4. Some models use 3, some 5. Larger expansion = more capacity but more parameters and compute. Balance between model power and training speed.
FFN has no cross-token communication. Token 1's FFN output depends only on token 1's post-attention vector, not on any other token. This is different from attention, which explicitly mixes. Together, attention (communication) + FFN (reasoning) form a complete block.

class Block(nn.Module):
    # One transformer layer: attention + FFN with residuals and layer norms

    def __init__(self, config):
        super().__init__()
        # Pre-norm: apply LayerNorm before each sub-layer
        self.ln1 = nn.LayerNorm(config.n_embd)  # normalize before attention
        self.attn = CausalSelfAttention(config)
        self.ln2 = nn.LayerNorm(config.n_embd)  # normalize before FFN
        self.mlp = MLP(config)  # expand-ReLU-compress

    def forward(self, x):
        # Input: x shape (B, T, C) = (12, 1024, 384)

        # ═══════════════════════════════════════
        # Block 1: Self-Attention + Residual
        # ═══════════════════════════════════════

        # Pre-norm: normalize before attention (more stable)
        normalized = self.ln1(x)  # (B, T, C)

        # Multi-head self-attention (gather context)
        attn_out = self.attn(normalized)  # (B, T, C)

        # Residual addition: preserve original info + apply correction
        x = x + attn_out  # (B, T, C)

        # ═══════════════════════════════════════
        # Block 2: Feed-Forward + Residual
        # ═══════════════════════════════════════

        # Pre-norm: normalize before FFN
        normalized = self.ln2(x)  # (B, T, C)

        # Feed-forward: per-token reasoning
        ff_out = self.mlp(normalized)  # (B, T, C)

        # Residual addition: preserve + refine
        x = x + ff_out  # (B, T, C)

        # Output: same shape as input, but richer representation
        return x

def train_step(model, batch_x, batch_y, optimizer, device):
    # batch_x shape: (B, T) token IDs
    # batch_y shape: (B, T) next-token labels (shifted x by 1)
    # Example: if batch_x = [1, 2, 3, 4], batch_y = [2, 3, 4, 5]

    # ─── Forward pass ───
    logits = model(batch_x)  # shape: (B, T, V) = (12, 1024, 50257)

    # Reshape for loss computation
    B, T, V = logits.shape
    logits_flat = logits.view(B * T, V)  # (12288, 50257)
    labels_flat = batch_y.view(B * T)    # (12288,)

    # ─── Loss computation ───
    # Cross-entropy: -log(P(correct_token))
    loss = torch.nn.functional.cross_entropy(logits_flat, labels_flat)

    # ─── Backward pass ───
    optimizer.zero_grad()      # clear old gradients
    loss.backward()            # compute gradients via backprop
    torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)  # clip to prevent explosion

    # ─── Weight update ───
    optimizer.step()           # apply gradient updates

    return loss.item()


def cross_entropy_loss_example():
    # Tiny example: vocabulary of 5 tokens, model predicts logits for one token

    vocab_tokens = ["cat", "dog", "sat", "the", "mat"]
    logits = torch.tensor([0.5, -0.3, 2.1, 0.8, 0.1])  # model's output
    true_token_idx = 2  # correct answer is "sat"

    # Step 1: softmax to get probabilities
    probs = torch.softmax(logits, dim=0)
    # probs ≈ [0.14, 0.08, 0.48, 0.21, 0.09]  (sum to 1)

    # Step 2: cross-entropy = -log(probability of true token)
    loss = -torch.log(probs[true_token_idx])
    # loss ≈ -log(0.48) ≈ 0.73

    # Lower probability → higher loss → stronger gradient signal
    # If model had assigned prob 0.99 to "sat": loss ≈ -log(0.99) ≈ 0.01 ← small loss, good!
    return loss
★
Key concepts
Cross-entropy loss measures surprise. If the model assigns 90% probability to the correct token, loss = -log(0.9) ≈ 0.11. If it assigns 10%, loss = -log(0.1) ≈ 2.3. Larger errors produce larger losses, driving strong gradient updates.
Causal masking in training. During training, the model must predict token t using only tokens 0...t-1 (no peeking ahead). At inference time, tokens t+1 onwards don't exist. Training mirrors this constraint to prevent the model from learning to use future information.
AdamW optimizer. PyTorch's AdamW combines Adam (adaptive per-parameter learning rates) with decoupled weight decay. It is the standard optimizer for transformers because it converges faster and more reliably than vanilla SGD.
Gradient clipping prevents explosion. Even with residuals and layer norm, gradients can occasionally spike. If the max gradient is, say, 50 but we clip to 1.0, all gradients are scaled down proportionally. This prevents catastrophic updates that destabilize training.

Generation: Autoregressive Sampling and Decoding
How the trained model generates text one token at a time, with temperature and nucleus sampling for control
?
Why it works

After training, the model can generate new text by running in a loop. Start with a prompt, feed it through 12 transformer layers to get logits for the next token. Sample (or greedily pick) a token from the distribution, append it to the input, and repeat. Each generated token becomes part of the context for predicting the next one. This is called autoregressive generation because each output becomes an input.

def generate(model, prompt_ids, max_new_tokens=100, temperature=0.8,
              top_p=0.9, device="cuda"):
    # prompt_ids: list of token IDs, shape (1, prompt_len)
    # temperature: controls randomness (0=greedy, 1=normal, 2=wild)
    # top_p: nucleus sampling (keep top p probability mass)

    model.eval()
    generated = prompt_ids.clone()  # copy to avoid modifying input

    with torch.no_grad():
        for _ in range(max_new_tokens):
            # ─── Forward pass: predict next token ───
            logits = model(generated[:, -1024:])  # keep last 1024 tokens (context window)
            next_logits = logits[0, -1, :]  # shape: (50257,) — last token's logits

            # ─── Apply temperature ───
            # Higher temperature makes distribution flatter
            # Lower temperature makes it sharper (more greedy)
            next_logits = next_logits / temperature

            # ─── Apply softmax to get probabilities ───
            probs = torch.softmax(next_logits, dim=-1)

            # ─── Nucleus (top-p) sampling ───
            sorted_probs, sorted_indices = torch.sort(probs, descending=True)
            cumsum = torch.cumsum(sorted_probs, dim=-1)

            # Find threshold: keep top tokens until cumsum exceeds top_p
            mask = cumsum < top_p
            mask[0] = True  # always keep at least the most likely token

            # Zero out probabilities below threshold
            filtered_probs = sorted_probs.clone()
            filtered_probs[~mask] = 0

            # Renormalize after filtering
            filtered_probs = filtered_probs / filtered_probs.sum()

            # ─── Sample from filtered distribution ───
            next_token = torch.multinomial(filtered_probs, num_samples=1)
            # Map back to original index
            next_token = sorted_indices[next_token]

            # ─── Append and continue ───
            generated = torch.cat([generated, next_token.unsqueeze(0)], dim=1)

            # Early stop if END token generated
            if next_token.item() == END_TOKEN_ID:
                break

    return generated

★
Decoding strategies
Temperature: Dividing logits by T before softmax changes the distribution. T=1 is normal. T=0.1 makes it sharper (greedy-like, deterministic). T=2 makes it flatter (wild, unpredictable). Most use 0.7–0.9 for a balance.
Top-p (nucleus sampling): Instead of sampling from all 50,257 tokens, filter to keep only the top tokens until cumulative probability reaches p (e.g. 0.9). This removes the "long tail" of unlikely tokens that add noise while preserving the model's confident choices.
KV cache optimization: In production, you don't recompute all Q, K, V projections for old tokens every iteration. You cache K and V from previous steps and only compute Q for the new token. This speeds up generation 10–100× and is essential for chat interfaces.

Encoder-Decoder Architecture for Translation
When and why to use bidirectional encoding and cross-attention for tasks like machine translation
?
Why it exists

Some tasks require fully understanding the source before generating the target (e.g., machine translation). Encoder-decoder architectures separate reading from writing: the encoder reads the entire source with no causal mask (seeing both past and future), producing rich source representations. The decoder then generates the target one token at a time using cross-attention to look up information in the encoder output. GPT and Claude are decoder-only and do not use cross-attention; they are optimized for next-token prediction in a single language.

# In a decoder layer, three separate attention mechanisms:

def decoder_layer_forward(x_decoder, encoder_output):
    # x_decoder shape: (B, T_tgt, C)  — decoder states so far
    # encoder_output shape: (B, T_src, C)  — frozen encoder output

    # ─── 1. Self-attention (causal) ───
    # Q, K, V all come from decoder
    # Causal mask: token i only attends to tokens 0..i (not future)
    self_attn_out = causal_self_attention(x_decoder)  # (B, T_tgt, C)
    x_decoder = x_decoder + self_attn_out  # residual
    x_decoder = layer_norm(x_decoder)

    # ─── 2. Cross-attention (decoder → encoder) ───
    # Q comes from decoder (what am I generating?)
    # K, V come from encoder (where should I look in source?)
    # NO causal mask: all decoder positions can attend to all source positions
    Q = W_Q @ x_decoder  # (B, T_tgt, C)
    K = W_K @ encoder_output  # (B, T_src, C)
    V = W_V @ encoder_output  # (B, T_src, C)

    scores = (Q @ K.transpose(-2, -1)) / math.sqrt(d_k)  # (B, T_tgt, T_src)
    # No masking! Decoder can look at all source tokens.
    weights = torch.softmax(scores, dim=-1)  # (B, T_tgt, T_src)
    cross_attn_out = weights @ V  # (B, T_tgt, C)

    x_decoder = x_decoder + cross_attn_out  # residual
    x_decoder = layer_norm(x_decoder)

    # ─── 3. Feed-forward (independent per token) ───
    ff_out = mlp(x_decoder)  # (B, T_tgt, C)
    x_decoder = x_decoder + ff_out  # residual
    x_decoder = layer_norm(x_decoder)

    return x_decoder


# Key difference from GPT (decoder-only):
# GPT: Self-attention only (Q, K, V from same source, causal mask)
# Encoder-Decoder: Three attention sub-layers, with cross-attention
★
Key distinctions
Decoder-only (GPT, Claude, LLaMA): All attention is causal self-attention within the same token stream. The model reads and writes in the same space. Optimized for next-token prediction in a single context. Simpler architecture, easier to scale.
Encoder-Decoder (original Transformer, T5, MarianMT): Encoder reads full source bidirectionally, decoder generates output with causal self-attention plus cross-attention into encoder. Better for tasks where you must fully understand input before output (translation, summarization). More complex, but can be more accurate for paired input-output tasks.
Cross-attention is the bridge. The decoder's Query asks "what do I need?", the encoder's Keys and Values answer "here is what exists in the source." This explicit lookup mechanism makes encoder-decoder models interpretable — you can see which source tokens the decoder attended to.

From embeddings to attention — a 15-year journey of iterative refinement
◆
The journey
THE EVOLUTION OF CONTEXT
2013 — WORD2VEC
═════════════════════════════════════════════════════════════════════
  Problem: How do we represent meaning as numbers?
  Solution: Train a shallow network to predict context words.
  Result:  Embeddings. "king - man + woman ≈ queen"

  Key insight: A word's meaning is captured in the geometry of its
               embedding vector. Similar words cluster together.
               But the embedding is STATIC — "bank" always gets
               the same vector regardless of sentence context.


2014-2017 — RECURRENT NEURAL NETWORKS (RNN, LSTM)
═════════════════════════════════════════════════════════════════════
  Problem: How do we process sequences and maintain context?
  Solution: Maintain a hidden state that updates as you read each word.
  Result:  Contextual representations! "bank" in "river bank" gets
           a different hidden state than in "deposit bank".

  Key insight: A hidden state vector accumulates information over time.
               But sequential processing is slow, and gradients vanish
               over long distances (RNN) or need special plumbing (LSTM).
               The cell state is like a protected highway that carries
               important facts forward unchanged.


2017 — TRANSFORMER WITH SELF-ATTENTION
═════════════════════════════════════════════════════════════════════
  Problem: RNNs are sequential (slow), and long-range dependencies vanish.
  Solution: Let every token directly attend to every other token in
             parallel. No sequential bottleneck!
  Result:  "bank" sees "flooded" immediately, not through 50 intermediate
           states. All tokens processed simultaneously. 10-100× speedup.

  Key insight: Context is not a single bottleneck vector (hidden state).
               Context is a rich, dynamic mixture of all other tokens'
               representations, weighted by learned relevance (attention).

               Attention is the same projection idea as Word2Vec (W1, W2)
               but applied THREE WAYS simultaneously:
               - W_Q:  "What am I looking for?" (like W1)
               - W_K:  "What do I offer?" (like W2)
               - W_V:  "Here is my content!" (NEW — not in Word2Vec)


UNIFYING INSIGHT: CONTEXTUAL AGGREGATION
═════════════════════════════════════════════════════════════════════

All architectures solve one problem:
  "Given a sequence of words, build a representation of meaning
   that lets you predict what comes next."

Each architecture's solution:
  Word2Vec:   Aggregate meaning across the training corpus
  RNN:        Aggregate meaning sequentially (past tokens only)
  LSTM:       Aggregate meaning sequentially with a protected highway
  Transformer: Aggregate meaning in parallel from ANY token to ANY token,
               weighted by learned relevance

The progression is about REMOVING BOTTLENECKS:
  Word2Vec:    One bottleneck (embedding)
  RNN:         One bottleneck (hidden state) per time step (slow!)
  LSTM:        One bottleneck per time step + cell state bypass
  Transformer: NO bottleneck — every token talks directly to every token
?
Why the Transformer won

Transformers unified the best ideas from their predecessors and parallelized everything. Word2Vec embeddings are still the entry point (wte). RNN's context accumulation is replaced by attention, which is more expressive and infinitely parallelizable. LSTM's cell state intuition becomes residual connections — a protected lane that carries information through depth rather than time. The result: a model that trains 100× faster than RNNs on the same data, learns longer-range dependencies, and scales to billions of parameters with predictable improvements.

★
Three directions forward
Scaling. Larger models (more parameters), more data (longer training), larger context windows. The Transformer scales gracefully — double the size, get predictable improvements in capability. GPT-2 (117M) → GPT-3 (175B) → future models (1T+). Chinchilla scaling laws suggest optimal models have roughly 20 tokens of training data per parameter.
Long context. Current Transformers have context windows of 1K-32K tokens (nanochat, GPT-3.5). New architectures (sparse attention, linear attention, RNNs with attention) are pushing toward 1M+ tokens. This unlocks whole-document reasoning, retrieval-augmented generation, and multi-turn conversations.
Efficiency. Full attention is O(T²) — expensive for long sequences. Alternatives: Linformers (linear complexity), Performers (kernel tricks), or returning to RNN-like recurrence for long context. Research is exploring how to get Transformer capability with RNN efficiency.
